# Rede de alocação — testes e limites

Execute `run.sh` com JAVA_HOME apontando para JDK 8, FORGE_MAPPED_JAR para o JAR Forge 1.12.2 mapeado e DEPS_CP para as dependências do Forge. O teste executa a máquina de replay real dos handlers e a serialização, não um servidor Minecraft. Simula conexões como estados independentes; não testa GUI, sockets, descarregamento por GC ou multiplayer ao vivo.

- O servidor só mantém o último token/resultado por conexão, para cada fluxo. Tokens antigos e payloads alterados são rejeitados; lacunas são aceitas para permitir uma barreira de leitura após timeout. O mapa usa chaves fracas: o espaço é O(conexões vivas), não O(pedidos); a liberação depende do GC.
- Reenvios de atributo e de habilidade usam o mesmo token. Após tentativas, uma leitura com sequência maior estabelece o estado e impede a execução posterior de uma compra anterior. Uma compra pode ter sido aplicada antes da barreira; isso é informado, sem inventar sucesso ou falha. Sem resposta à barreira de atributo, o fluxo para de tentar e os botões mudam para `?`: toque para tentar novamente; não executa outra compra. Sem comunicação não há como garantir simultaneamente disponibilidade e prevenção de compra duplicada.
- O registro de replay é volátil e vinculado à conexão, não é persistido no mundo. Reconexão abre uma conexão nova e a GUI busca dados autoritativos; pacotes da conexão antiga não são reaproveitados pelo cliente. Se um cliente adulterado retransmitir explicitamente um token antigo numa conexão nova, ou após reinício do servidor, o registro anterior não protege essa retransmissão. Falha do servidor entre alteração e gravação do mundo também não é transação durável.
- A alteração desativa a antiga mensagem sem token de compra de atributo: cliente e servidor devem executar esta mesma versão do mod. Cliente antigo não poderá alocar atributos; misturar versões não foi validado. Limites numéricos são fail-closed: sessão/sequência de habilidades são inteiros positivos (a sessão usa contador da JVM do cliente), sequência de atributos é long positivo; esgotamento exige reiniciar o cliente/conexão, não faz wrap silencioso.
- A fila é limitada a 16 tarefas por entidade, podendo descartar pedidos sob saturação. O cliente reenvia antes de passar à barreira; nenhuma entrega é prometida com a conexão indisponível ou continuamente saturada. O dono de uma tarefa e a dimensão são verificados antes da mutação; respawn/troca de dimensão pode descartar a tentativa antiga, depois reenviada. Nenhuma prova substitui teste em servidor dedicado e integrado real com respawn, troca de dimensão e reconexão.
